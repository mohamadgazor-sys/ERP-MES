# ERP/MES Project Instructions for Claude Code

## Start-of-session requirements
1. Work from the repository root.
2. Read the three authoritative documents in `docs/` before structural work:
   - `ERP_MES_CSharp_Master_Specification_Current_State.md`
   - `ERP_MES_CSharp_Architecture_Specification.md`
   - `ERP_MES_CSharp_Domain_and_Database_Specification.md`
3. Read `docs/DECISION_LOG.md` and the latest `docs/SESSION_LOG.md` entry, if present.
4. Do not rely on conversation memory as the project's source of truth.

## Authority and conflict handling
- Master Specification is authoritative for business requirements.
- Domain and Database Specification is authoritative for approved entities, relationships, constraints, and data ownership, provided it does not conflict with an explicit business decision in the Master Specification.
- Architecture Specification describes the intended technical design.
- If documents conflict, an approved decision is absent, or a requirement is ambiguous, stop before making a logic-changing decision. Explain the conflict, quote the relevant file/section, provide options and consequences, and ask the user.
- Never silently invent business rules. Mark assumptions explicitly and keep them out of production behavior until approved.
- Update relevant specifications and `docs/DECISION_LOG.md` when the user approves a business decision.

## Canonical business rules already decided
- Windows desktop application; WPF with MVVM; Persian UI, right-to-left layout.
- Target deployment is Windows 10/11 only. Do not support Windows 7 or Windows 8. Exact .NET version and Windows 10 baseline must be verified before framework lock-in.
- Development database is local SQLite for single-user development only. Production backend is SQL Server after approval. Keep business logic independent of database-provider details.
- Request is the central business container. Projects are not mandatory and the program must be request-based.
- There is no Internal Request workflow in v1 and no Emergency subsystem.
- One customer request can contain both MAKE and REPAIR items. `WorkTypeID` belongs to each item and is MAKE or REPAIR.
- Customer `RequestNo` is supplied by the customer, free-form text, not generated by the application. Business uniqueness is Customer + RequestNo + Jalali Request Year. Comparison is case-sensitive; do not trim/change case silently.
- If a request requires a contract, the contract applies to the entire request. Planning creates/submits the contract and PDF; Management approves/rejects with optional explanation. Rejection returns to Planning for correction/resubmission. After approval, notify Planning and Warehouse dashboards. Customer is derived from Request, not duplicated on Contract.
- QC approval of the immediately preceding stage is required before every subsequent stage can proceed. Planning normally releases the first internal stage. If the first stage is external supply, the system waits for return/arrival and QC approval before the next stage is released.
- External supply is represented as a production stage, with dispatch/arrival tracking and QC; quantities may be accepted or rejected. Permanently rejected quantity is scrap. Rework quantity returns through rework handling.
- A later QC correction preserves history and marks the item as corrected; send the item back to Stage 1 and let downstream stages be manually handled. Do not automatically invalidate/replay every downstream stage.
- All user-visible dates are Shamsi/Jalali, with 24-hour time. All currency values are Iranian Rial; never convert silently to Toman. Internal database date representation may be Gregorian/native if correctly converted at boundaries.
- QC owns configurable UOM definitions. Reciprocal conversions are automatically derived when the factor is positive/non-zero (e.g. PAIR→PCS 2 implies PCS→PAIR 0.5).
- Planning owns machine rate per hour and controls normal priority/order. Priority labels are exactly `عادی`, `فوری`, `خیلی فوری`; multiple items/stages may share a priority.
- Planning enters estimated machining time in minutes per piece. Estimated processing duration is minutes per piece × planned quantity, subject to configured working calendar, queue ordering, machine/unit capacity, downtime, and external lead time.
- Management alone may override multiple stages/items in a queue operation. Preserve Planning's underlying priority and log the manager, timestamp, old/new order for each affected row, and reason.
- Regular workdays are Saturday–Thursday; Friday is normally off but approved work/additional hours are possible with supervisor approval. Calendar, holidays/off-days and shift patterns must be configurable. Current schedule is 08:00–17:00 with 12:00–13:00 break; possible future patterns include two 8-hour shifts 06:00–14:00 and 14:00–22:00, and possibly three shifts. Do not hard-code these as permanent constants.
- PM reports machine downtime to Planning; downtime must affect the scheduling forecast and be auditable.
- External stages need expected lead time.
- Excel import is core v1: one mixed worksheet, Persian headers, explicit Work Type column, roughly 1,000 items, preview/validation, transactional import, and manual conflict choice if an existing ItemNo has changed values. Do not silently overwrite conflicts.
- Management needs a live production overview; the work queue must reflect Planning priority changes and authorized Management overrides.
- QC alone performs QC inspection/correction; Drawing alone makes technical doability decisions; Planning creates contracts; only Management approves/rejects contracts and initial requests; Warehouse alone receives items; Planning+Management can edit priorities; Management+Planning can maintain machine rates; Warehouse+Management can maintain material price/kg; only the Admin user administers users/roles.
- A stored PDF/document binary may be linked to multiple records. Store the binary once and represent each association explicitly; do not duplicate bytes for every logical link.
- Performance reward/ranking formula is Phase 2. v1 may build reporting infrastructure without calculating bonuses/rankings.

## Implementation safety rules
- Do not begin implementation until the documentation audit and implementation plan have been reviewed by the user.
- Before any change, identify affected layers, data, workflows, permissions, UI, migrations and tests. Keep changes small.
- Never run destructive commands, delete/overwrite user files, or modify source specifications without explicit approval.
- Do not install packages, run migrations, create the application skeleton, or write application code during a documentation-audit session unless the user explicitly authorizes it.
- Database operations must use transactions where multiple related records must change together. Preserve audit/history records.
- Use provider-compatible abstractions; do not rely on SQLite-only SQL or behavior in application/business logic.
- Use async/cancellation where appropriate for database/report calls; do not block the WPF UI with long-running work.
- Run builds and relevant tests after code changes. Report exact commands and actual results. Never claim build/test success without running them.
- At the end of every substantial session, update `docs/SESSION_LOG.md` with: completed work, changed files, decisions made, unresolved questions, tests actually run, known risks, and the exact recommended next action.
- Never place credentials, tokens, real passwords, live customer PDFs, or production database backups in Git.
