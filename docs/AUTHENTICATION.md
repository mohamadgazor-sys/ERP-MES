**Domain position (for your confirmation).** Architecture Specification 3.3 lists `User`, `Role` and `Department` among the Domain entities, but no Domain rule needs them: the Domain refers to a user only by id (`CreatedByUserId`). Following your instruction to keep authentication and account management out of the Domain unless the architecture explicitly assigns a domain responsibility there, the account model lives in Application (rules) and Infrastructure (storage). A test checks that the Domain contains no authentication or account behaviour. If you want `User` as a Domain entity after all, it can move without changing behaviour.

**No new package.** PBKDF2 (`Rfc2898DeriveBytes.Pbkdf2`), SHA-256, the random generator and constant-time comparison are in the .NET base library; settings use `System.Text.Json`. The `Microsoft.Extensions.*` packages listed in the Milestone 1 plan (options, configuration, DI) were **not** added, because each package batch needs your approval (Decision Log #43, #53); hand-written composition is used instead.

## 2. Password hashing (Decision Log #27, #41, #42)

- PBKDF2-HMAC-SHA256, initially **600,000 iterations**, a **fresh 16-byte random salt per password**, a 32-byte derived key.
- Stored per user: `PasswordHash`, `PasswordSalt`, `PasswordAlgorithm` (`PBKDF2-HMAC-SHA256`), `PasswordHashVersion` (1) and `PasswordWorkFactor`. Verification uses the stored values, never a global setting, and compares in constant time.
- After a successful sign-in, a hash whose algorithm, version or work factor is below the configured baseline is re-hashed and the change is audited (`PasswordHashUpgraded`). A failed attempt upgrades nothing. The work factor is never lowered automatically; values below 310,000 are refused at start-up.
- The password is used exactly as typed (UTF-8, no trimming, no normalisation).
- `benchmark-hash` times one hash on the machine where it runs (target about 500 ms on the lowest-spec supported PC, Decision Log #42). **It has not been run on that PC**: the PC is not identified yet, so 600,000 is still a starting value.
- Tests include the standard PBKDF2-HMAC-SHA256 vectors (computed independently of the code), per-password salts, stored-parameter verification and one real hash at the 600,000 baseline.

## 3. Sign-in, lockout and one-time passwords (Decision Log #40)

- Defaults: minimum password length 12 (counted in characters, no composition rules), 5 failed attempts, 5-minute lockout; all configurable, none below its floor (length >= 8, attempts 3-10, lockout >= 1 minute, iterations >= 310,000).
- The failed-attempt counter and the lockout end are columns of the user row, so they hold across every application instance that shares the database. Concurrent failures are all counted (the user row has a row version; a lost race is retried).
- Unknown user, wrong password and inactive account give the same answer; the response time does not reveal an unknown name (a dummy hash is verified). An existing locked account answers "locked" without checking the password, and the lock does not extend. The attempted name of an unknown user is **not** written to the audit log (people sometimes type a password into the name field).
- A password set by an administrator, or the initial password of a new account, is **one-time**: the user must choose their own before being let in (`MustChangePassword`). A wrong current password in the change form counts as a failed sign-in, so the form cannot be used to guess a password.

## 4. Administrator bootstrap (Decision Log #39; plan section 5)

- A freshly migrated database has one `SystemSetup` row, `NotProvisioned`, and no users (a check constraint keeps it a single row). The application never creates an administrator by itself; `NotProvisioned` shows "contact your administrator" and no input fields.
- `issue-admin-token --database <file> [--hours N]` (Provisioning) generates 32 random bytes from the operating-system generator, stores **only the SHA-256 digest** with an expiry (default 24 hours) and `AwaitingBootstrap`, audits it, and prints the token **once**. Issuing again replaces digest, expiry and counter, so the previous token stops working. It is refused once the system is initialised.
- Redeeming (first-run screen): input that is wrong in itself (user name, display name, password policy) is refused without using an attempt. Then **the attempt is counted in its own short transaction before the token is compared** (so guesses persist and the limit of 5 is central), the digests are compared in constant time, and the claim is a single conditional update of the setup row (row version) that also inserts the administrator (department System, role Admin). Of two simultaneous claims exactly one wins; the loser is told the system is already initialised.
- An expired token or the fifth wrong attempt withdraws the token (`NotProvisioned`); IT must issue a new one. After success the digest is erased and the bootstrap path is closed for good.

## 5. Administrator recovery (Decision Log #47; plan 5.7)

- `issue-recovery-token --database <file> --username <administrator> --reason <text>`: the target must be an existing Administrator account; a reason is required; the token is 256-bit random, only its digest is stored (24-hour expiry, 5 attempts) and it is printed once. The reason, machine and operating-system user are audited. Issuing again invalidates the previous token. The operator supplies the database at run time; nothing privileged is stored.
- The login screen offers "use recovery token" **only while a valid recovery token is pending**.
- Redeeming: the person enters the token and a **new** password. Same order as bootstrap (policy check, central attempt counting, constant-time comparison). Only after the token is accepted is the new password compared with the old one, so a caller without the token learns nothing about the old password; an unchanged password is refused and the token stays valid. One conditional update then sets the new hash (fresh salt, current work factor), reactivates the account, sets the Administrator role, clears the counter and lockout, erases the token and advances the administrator stamp. Of two simultaneous redemptions exactly one succeeds.
- There is no universal recovery password, master key or backdoor; tests search the source for such constructs (comments excluded).

## 6. Account administration and the last administrator

- Only the Admin role administers accounts (Domain and Database Specification 15.2). Every administrative method **reloads the acting user from the database** and checks that they are an active Administrator, so a stale or forged principal grants nothing.
- Users are never physically deleted: deactivate instead. Every foreign key restricts deletion.
- The last active Administrator can be neither deactivated nor demoted. The check and the change run in one transaction that also advances `SystemSetup.AdminChangeStamp`, so of two concurrent removals one fails and is re-evaluated against the new state (`LastAdministrator`). A refusal is audited (`LastAdminProtectionRefused`). Recovery does not need the application's account screens, so it is not blocked by this rule.

## 7. Authorization (default deny)

`AuthorizationRules` maps each action to departments and, where the specification says so, a role. The rows are exactly those of Domain and Database Specification 15.2 and the provisional development map 15.4 (Decision Log #34):

| Action | Department / role |
|---|---|
| Administer users | Role Admin (any department) |
| Initial request approve/reject | Management **and** Manager |
| Drawing doability decision; define MAKE items | Drawing |
| Create/submit contract; maintain calendar; receive/edit request details; define REPAIR items and edit any item | Planning |
| Approve/reject contract; override queue order | Management |
| QC inspect/correct; maintain units of measure | QC |
| Change Planning priority; change machine rates; reopen a rejected request | Planning or Management |
| Change material price per kg | Warehouse or Management |
| Final warehouse receipt | Warehouse |
| Register downtime | Maintenance/PM |
| Create/submit a request | Central |
| Import items from Excel | Planning or Drawing |

Everything else is denied, including for the Admin role (it administers accounts and nothing else), for an unknown permission, a missing department or role, and an inactive user. The expected table is written out a second time in the tests and compared for every department x role combination. **No screen calls these rules yet** (no customer/request/queue/QC screens exist); the UI will mirror the rule, and the use case at the boundary will enforce it. "Planning reviews downtime" is deliberately **not** mapped, because the specification leaves that workflow open.

## 8. Audit log

`AuditLog` (append-only: the persistence layer rejects an update or delete of an entry) records time, user (when known), machine, operating-system user, optional database login, action code, target and a summary. Actions: login success/failure, lockout and unlock, password change/reset/upgrade, user created/activated/deactivated/role changed, last-administrator refusal, and the bootstrap and recovery events of plan 5.6. Tokens and passwords never appear in an entry (tests check this). SQLite reports no database login, so that column stays empty; **append-only is enforced in code, not by database triggers or permissions** (provider-specific protection belongs to the future production database design).

## 9. The demonstration accounts (T6) and `CreatedByUserId`

`DemoAccountProvisioner` creates the fictional accounts **only through the production use cases**: the first administrator comes from the real bootstrap path (a token issued and redeemed inside the process, never printed or stored), and the other six accounts are created by that administrator through `AccountService`. Each of the seven accounts (`demo.admin` in System/Admin, and one user for Central, Management (Manager), Planning, Drawing, QC and Warehouse) gets a random 20-character password from the operating-system generator, different per account and per provisioning, and each is one-time (change at first sign-in).

- The passwords are written **only** to a credential file: outside any Git working tree (a path inside one is refused before anything is built), never overwriting a file, created with a protected access list for the current Windows user only (mode 0600 elsewhere), name pattern `*.credentials.txt` ignored by Git. By default the file goes under the user's local application data; `--credentials <file>` chooses another. They are never printed by Provisioning, never logged, and not committed. CI masks them and checks that no command output contains them.
- `demo-init` on an existing, already-initialised demonstration database creates no accounts and no file. `demo-reset` replaces the database with new accounts and new passwords. A database marked as a demonstration database but seeded **before** accounts existed is refused with "reset it".

**Reconciling the placeholder `1`.** Earlier, the sample data stored `CreatedByUserId = 1` and `ApprovedByUserId = 1` as a label although no user existed. That placeholder is gone: the seed now takes two real user ids (the `demo.central` account "created" the customers, requests and items; the `demo.qc` account "approved" the stages), provisioned before the seed runs. A test checks that every created-by and approved-by value in the sample data refers to an existing user row, and that the creators are exactly those two accounts (the value 1 now happens to be `demo.admin`, which creates nothing in the sample data).

**No foreign key was added to those columns** (open mapping question M10 in `docs/PERSISTENCE_MAPPING.md`). A real foreign key from `CreatedByUserId` to `Users` would be the integrity-correct design, but it would alter the accepted tables (SQLite rebuilds a table to add a key), and every existing persistence test uses user ids without user rows. It needs your decision; until then the columns are plain numbers whose values are, for the demonstration data, verified to be real users.

## 10. Configuration

`appsettings.json` (Desktop, committed, non-secret) holds the approved defaults; `appsettings.Local.json` (ignored by Git) may override single settings. An unknown setting name is an error (a misspelt security setting must not silently fall back to a default), and a value below its floor stops the application. The database file is `%LocalAppData%\ERP-MES\erpmes.demo.db` unless the environment variable `ERPMES_DATABASE` names another. The application **never creates or resets a database**; it only applies pending migrations to an existing file (the normal start-up path). Policy in the database for multi-PC deployment is deferred (Decision Log, Unresolved).

## 11. Implementation assumptions for your confirmation

These are choices the approved text does not settle. None is recorded as a decision.

| # | Assumption | Why |
|---|---|---|
| A1 | User names are stored and compared exactly (case-sensitive, never trimmed); names with white space or control characters, empty names, and names over 64 characters are rejected. | Same philosophy as `RequestNo`; avoids look-alike accounts. Case-insensitive uniqueness would be a separate decision. |
| A2 | The token is 32 random bytes shown as 64 hexadecimal digits in groups of 8; case, dashes and spaces are ignored when typing. | Easy to read aloud and type; the entropy is 256 bits. |
| A3 | Initial passwords of new accounts and administrator-reset passwords are one-time (the user must choose their own at the first sign-in). The password chosen at bootstrap or recovery is the user's own. | "One-time passwords" for the demonstration accounts (T6); "forces the recovered account to set a new password" (#47). |
| A4 | An existing locked account answers "locked" (not the generic answer). | Usability; it discloses that the name exists. |
| A5 | The first administrator's department is System (Decision Log #30). | Home of the Admin account. |
| A6 | `Departments` and `Roles` hold the development seed names (my Persian wording) in the migration; code uses the stable codes. | #30 says final names may replace them without a schema change. |
| A7 | Audit append-only is enforced in code only. | See section 8. |
| A8 | The application applies pending migrations to an existing database at start-up and never creates one. | Normal start-up path of the persistence plan; creation stays with IT. |
