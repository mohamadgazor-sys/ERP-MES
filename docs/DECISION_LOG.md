# ERP/MES Decision Log

This is a durable record of user-approved decisions. Update it only when the user approves a decision. Keep unresolved items in the separate section below.

## Approved decisions

1. **Request identity:** Customer-provided free-form RequestNo; not generated internally. Unique business key is Customer + RequestNo + Jalali Request Year. RequestNo comparison is case-sensitive. RequestID is the internal primary key.
2. **Request/item model:** Request-based system; no mandatory Project entity. Customer requests may contain both MAKE and REPAIR items. WorkTypeID is at item level. *[Note added by #84: superseded for the intended production system - a request has exactly one authoritative work type and mixed-type requests are prohibited; the demonstration keeps its current data until the lifecycle PR replaces it. The text above is kept as history.]*
3. **Excluded scope:** No Internal Request workflow in v1; no Emergency subsystem; no Final-QC concept. QC is required after individual production stages.
4. **Contracts:** Contract requirement applies to the entire request. Planning creates/submits the contract and attaches/imports PDF. Management approves/rejects with optional explanation. Rejected contracts return to Planning for correction/resubmission. Approval notifies Planning and Warehouse dashboards. Contract customer is derived from Request. *[Note added by #85: superseded - the contract determination applies to MAKE requests only; a pure REPAIR request skips it. The text above is kept as history.]*
5. **Production/QC:** Each subsequent stage waits for QC approval of the immediately preceding stage. Planning normally releases the first internal stage. If first stage is external, wait for arrival/return and QC approval before progressing. External supply is a stage with dispatch/arrival tracking and QC.
6. **QC correction:** Preserve the historical QC decision and mark the item as corrected. Return the item to Stage 1; handle downstream stages manually rather than automatically replaying every downstream stage.
7. **Quantities:** QC permanently rejected quantities are scrap. Accepted quantities continue; only rework quantity returns for rework.
8. **Localization:** Every user-visible date is Shamsi/Jalali with 24-hour time. Every monetary value is Rial, never silently Toman. UI is Persian and RTL.
9. **UOM ownership:** QC defines configurable units/conversions. A positive conversion factor implies its reciprocal automatically.
10. **Cost ownership:** Planning maintains machine machining rate/hour. Warehouse maintains raw-material price/kg.
11. **Priority:** Values are `عادی`, `فوری`, `خیلی فوری`. Planning owns normal priority/order and may change it; multiple stages/items may share a priority. Management alone may batch-override queue order. Every affected row records old/new order, reason, manager, timestamp; original Planning priority remains intact. (Where the Planning priority is stored: #58.)
12. **Machining time:** Planning enters minutes per piece. Estimated stage load is minutes per piece × planned quantity.
13. **Calendar:** Saturday–Thursday are normal workdays. Friday is normally off but may be worked with supervisor approval. Holidays/off-days and shift patterns are configurable. Current reference schedule: 08:00–17:00 with 12:00–13:00 break; a possible 2-shift setup is 06:00–14:00 and 14:00–22:00; more shifts may be introduced. Do not hard-code current settings permanently.
14. **Downtime:** PM reports machine downtime to Planning; approved/recorded downtime affects planned end calculations.
15. **External lead time:** External production stages require expected lead time.
16. **Excel:** One mixed worksheet, Persian headers, explicit Work Type column, about 1,000 items. Preview/validate before import. Existing same-ItemNo rows with changed imported values are manual-choice conflicts, not silent overwrites.
17. **Warehouse scope:** Inquiry/receipt/movement history only; no real inventory balance/deduction system in v1.
18. **PDF/document links:** Store a document binary once and permit multiple logical record links.
19. **Authentication/roles:** Application username/password; one department and one role per user. Sensitive action permissions are defined in the Domain and Database Specification §15.2 / §32.8 and the project instructions (`CLAUDE.md`).
20. **Platform/data migration:** Windows 10/11 desktop; WPF/MVVM; local SQLite only for single-user development; final production database SQL Server. Confirm supported Windows 10 baselines and exact .NET target before locking framework.
21. **Performance bonuses:** Ranking/reward formula is Phase 2, not a v1 approval/payroll calculation.
22. **Initial .NET target (approved 2026-10-09; amended 2026-10-10; initial, not a production lock):** .NET 10 (LTS). Per the official Microsoft .NET support policy checked on 2026-10-10 (https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core): .NET 10 is LTS, released 2025-11-11, supported until 2028-11-14 (latest patch listed there: 10.0.12). Target frameworks: `net10.0-windows` for the WPF Desktop project; `net10.0` for platform-neutral class libraries (Domain, Application, Infrastructure and test projects) as applicable. This does not settle the Windows baseline or the SQL Server version: the minimum supported Windows edition/version and the production SQL Server version remain unresolved (see Unresolved) until the deployment environment is checked. Microsoft's .NET 10 supported-OS list (https://github.com/dotnet/core/blob/main/release-notes/10.0/supported-os.md) names only specific Windows 10 builds/servicing channels, not all Windows 10 editions, so no blanket Windows 10 support is claimed.
23. **Keys and concurrency (approved 2026-10-09):** Integer surrogate primary keys (Domain and Database Specification §25.1). Mutable entities carry an application-managed row-version column used for optimistic concurrency, portable between SQLite and SQL Server.
24. **Time storage (approved 2026-10-09):** Timestamps are stored in UTC; calendar-only dates (for example request date) use a date-only type. Conversion to Jalali and local time happens only at the presentation boundary.
25. **Provider conventions (approved 2026-10-09):** Maintain a written provider-neutral subset (no SQLite-only SQL in business logic; avoid decimal aggregates, `DateTimeOffset` and partial indexes in business queries). Keep one EF migration set per provider. The SQLite development database is disposable and is not migrated to production. Run a SQL Server test pass before the stage/QC milestone.
26. **Audit (approved 2026-10-09):** A generic append-only audit table records master-data, configuration and login events, in addition to the domain-specific histories already required (workflow entries, QC, queue overrides, etc.).
27. **Password storage (approved 2026-10-09):** PBKDF2 using the built-in .NET implementation, with a per-user random salt and the iteration count stored with the hash so it can be raised later. Passwords are never stored in plaintext. Parameters are fixed in the Milestone 1 ADR.
28. **Documentation amendments (approved 2026-10-09):** Superseded passages in the specifications are annotated, not rewritten, and mechanical errors (wrong section numbers, stray markers, stale cross-references) are corrected. No business rule text is changed by an amendment. Items that still need an owner decision are left open.
29. **Request statuses for Milestone 2 (D5, approved 2026-10-10):** The initial request-status set is `CREATED`, `SENT_TO_MANAGEMENT`, `MGMT_APPROVED_AT_PLANNING`, `MGMT_REJECTED_AT_PLANNING`, `UNDER_DRAWING_REVIEW`, `DRAWING_RETURNED_TO_PLANNING`, `CANCELLED`, `CLOSED`. Management rejection requires a reason. A Management-rejected request **can be reopened** for a new Management decision by the Planning department or the Management department; reopening requires a reason and is audited. Later statuses (contract, production, completion) are added with their milestones. The full transition table is still to be drafted from Master Specification §3 and audit Appendix A and reviewed at the start of Milestone 2 (see Unresolved).
30. **Departments and roles seed (D6, approved 2026-10-10, development seed):** Departments: Central, Management, Planning, Drawing, Warehouse, Production, QC, Maintenance/PM, and System (home of the Admin account). Roles: Admin, Manager, Staff. Final company names may replace these without a schema change. Authorization rows that name a role use these names (initial request approval/rejection = Management department + Manager role); all other matrix rows remain department-based as in Domain and Database Specification §15.2.
31. **RequestNo key details (D7, approved 2026-10-10):** (a) The Jalali Request Year is derived from the customer's `RequestDate`, fixed at creation, and changeable only through an audited correction that re-checks uniqueness. (b) Leading or trailing whitespace in `RequestNo` is rejected with a validation error, never auto-trimmed. (c) No letter or digit normalisation is applied to `RequestNo`; it is stored and compared as exact text. (d) `RequestNo` uses a case-sensitive binary collation on both SQLite and SQL Server, verified by a test on both providers. (e) A non-blocking warning is shown when a case-insensitive near-duplicate exists for the same customer and Jalali year.
32. **Customer master (D8, approved 2026-10-10):** Minimum fields: `CustomerID`, `Name`, `IsActive`, and created/updated audit fields. No customer code and no contact fields for now (added later when a requirement exists). "Customer" is the canonical term ("Buyer" is legacy). There is no item-level customer; an item's customer is its request's customer.
33. **Quantity precision (D9, approved 2026-10-10):** Requested quantities, UOM conversion factors/results and minutes-per-piece are stored as decimals with a fixed scale; the scale is set in the Milestone 2 design (proposal: 4 decimal places). Per-UOM whole-number rules may be added later. Decision #25 still applies (avoid decimal aggregates in business queries). Rial rounding and storage type remain unresolved.
34. **Provisional development permission map (D10, approved 2026-10-10; revisit before production):** Central creates a request and submits it to Management. Planning receives the request, records the hand-off to Drawing, and edits request details. Drawing records the doability decision (already in the matrix) and defines MAKE items. Planning defines REPAIR items and may create/edit any item. Planning and Drawing may import items from Excel. Items are editable only until production release; after release only Planning may change them, through the controlled route-revision mechanism that is still to be specified. Every action not listed here or in Domain and Database Specification §15.2 remains denied. *[Note added by #84/#86/#89: the mixed MAKE/REPAIR rule and "Drawing defines MAKE items" are superseded for the intended production system (single type per request; Planning defines all items and stages after the gates; Drawing owns feasibility and raw-material inquiries). Content-hash de-duplication on upload and retention/deletion rules are not decided here.
36. **Milestone 1 scope (P1, approved 2026-10-11):** Milestone 1 is limited to the technical foundation. It does not implement Customer, Request, RequestItem, request workflow, Excel import, MAKE/REPAIR functionality, documents, or any production functionality. Architecture Specification §38 reflects this scope.
37. **Project structure (P2, approved 2026-10-11, subject to documented responsibilities):** Projects `Domain`, `Application`, `Infrastructure` (shared, provider-neutral), `Infrastructure.Sqlite`, `Desktop` and `Provisioning`, with the dependency direction and per-project responsibilities documented in `docs/MILESTONE_1_PLAN.md` §2. `Domain` remains independent of infrastructure and UI. Provider-specific persistence (configuration and migrations) belongs in provider-specific projects. A future `Infrastructure.SqlServer` project would add its own configuration and separate migrations beside `Infrastructure.Sqlite` without duplicating business logic (which lives only in Domain and Application); it is not created now, and the production SQL Server version/provider stays unresolved.
38. **Provisioning project (P3, approved 2026-10-11):** A separate `Provisioning` project, excluded from the normal factory-PC distribution. It supports authorized initial setup and administrator recovery. It must not embed privileged credentials; the operator supplies the database connection at run time.
39. **Administrator bootstrap (P4, approved 2026-10-11 with safeguards):** The first Administrator is created only with a cryptographically random, single-use bootstrap token. Only a digest of the token is stored, never the plaintext. The token expires after 24 hours and allows five attempts; the attempt limit is enforced centrally in the database across all application instances. Re-issuing a token invalidates the previous one. The claim is atomic so two clients cannot both create the initial Administrator. The token is never logged and never committed to source control. No default password or credential exists in the repository.
40. **Authentication policy (P5, approved provisionally 2026-10-11):** Minimum password length 12 (superseded by #72: minimum 6, no white space), five failed attempts, five-minute lockout. All values are configurable. Security events are audited.
41. **Password hashing (P6, approved 2026-10-11):** PBKDF2-HMAC-SHA256, initially 600,000 iterations, a fresh random salt per password. Stored per password: algorithm and version, salt, iteration count and derived hash. Older parameters are upgraded after successful password verification. The baseline is not changed silently. (Supersedes the parameters left to the Milestone 1 ADR in #27.)

61. **Identity and organisation concepts belong to the Domain (owner correction of PR #19, 2026-10-15):** `User`, `Role` and `Department` - with their stable codes, the login-name value object and their invariants (exactly one department and one role per user, non-empty names, UTC timestamps, users deactivated and never deleted) - are in `ERP.MES.Domain`, as Architecture Specification section 3.3 lists them. Sign-in, bootstrap, recovery, account administration, the authorization use cases and their orchestration stay in Application; password hashing, credential storage (hash, salt, algorithm, version, work factor, lockout counters, the one-time flag), token handling, EF Core mappings and database operations stay in Infrastructure (and the credential record in Application). 62. **User names (A1, owner decision 2026-10-15):** Lookup and uniqueness ignore case, through one canonical key (the name in upper case, invariant culture) that the Domain `Username` computes and the database stores in a unique column, so the application and the database apply exactly one rule (no database collation decides). The name is stored as typed. Leading or trailing white space is rejected, never silently trimmed; control characters, an empty name and more than 64 characters are rejected. No Unicode normalization (for example Arabic versus Persian letter forms) is applied; that is not decided.
63. **Bootstrap and recovery token format (A2, owner decision 2026-10-15):** A 256-bit random token from the operating-system generator, written as 64 hexadecimal digits in groups of 8 separated by dashes; when typed, case, dashes and spaces are ignored. Only the SHA-256 digest is stored and compared in constant time.
64. **One-time credentials (A3, owner decision 2026-10-15):** The initial password of a new account and a password reset by an administrator are one-time credentials: the recipient must choose a new password before normal use. The password chosen during bootstrap or recovery is the person's own.
65. **Generic sign-in failure (A4, owner decision 2026-10-15; supersedes the distinct locked-account answer):** Unknown user, wrong password, inactive account and locked account give the caller the same generic failure. The audit log keeps the internal distinctions. Every one of those cases performs one password verification, so response time does not reveal which it was, and an attempt on a locked account never changes the credential, so it cannot extend the lockout. The change-password form follows the same rule.
66. **First administrator (A5, owner decision 2026-10-15):** The first Administrator, created by the bootstrap, belongs to the System department (consistent with #30).

69. **Start-up migration policy (A8, owner decision 2026-10-15):** For the local SQLite application, normal start-up may apply pending migrations to an existing database but never silently creates, seeds or resets one. The production migration policy remains undecided.
70. **Actor references are foreign keys (M10, owner decision 2026-10-15):** `CreatedByUserId` of customers, requests and request items and `ApprovedByUserId` of QC approvals are foreign keys to `Users` with deletion restricted; the optional actor references of the authentication schema (audit entry user, pending recovery target) are nullable foreign keys because an event can genuinely have no known user. 72. **Password policy: minimum 6 characters, no white space (owner decision 2026-10-16, refined 2026-10-16 before merge; supersedes the minimum length of 12 in #40):** The minimum password length is 6 characters (counted in characters, not bytes). **No Unicode white-space character is allowed anywhere in a password**, including at the beginning or end: ordinary space, no-break space, ideographic space, tab, line breaks and every other character for which .NET `char.IsWhiteSpace` is true. Such a password is rejected, never trimmed or normalised. Every other character is allowed (letters of any case or script, digits, punctuation, symbols), including the Persian zero-width non-joiner U+200C, which is not white space; no combination of character kinds is required. One policy applies wherever a user chooses a new password: the initial password, a password change, administrator reset, bootstrap and recovery. Signing in only verifies an existing password and never applies this policy. Generated one-time demonstration passwords stay 20 random characters and are valid under it. Unchanged: PBKDF2-HMAC-SHA256 (600,000 iterations, per-password salt), constant-time verification, hash upgrade, lockout, generic sign-in failure, token formats and limits, the rule that a recovery password differs from the current one, audit, default-deny authorization, credential-file protection and last-active-Administrator protection. Implementation note: the configurable safety floor for `MinimumPasswordLength` is lowered from 8 to 6, and the white-space rule cannot be configured away.

73. **JalaliDateService presentation and input (Q1-Q6, owner decision 2026-10-16):** (Q1) Dates and times are shown with **Persian digits**. (Q2) The local time zone is **Iran Standard Time** (Windows identifier `Iran Standard Time`, UTC+03:30; Iran has had no daylight saving since 2022), fixed by the application, not taken from the PC's own setting; stored timestamps remain UTC (#24). (Q3) Date and date-time **input accepts Latin, Persian and Arabic-Indic digits (U+0660 to U+0669), alone or mixed, and ignores white space before and after the text** (every `char.IsWhiteSpace` character); white space inside the text is still rejected, and the separators `-` and `.` and seconds are **not** accepted. This applies to dates only: it changes nothing for `RequestNo` (#31), user names or passwords (#72). (Q4) Display format `yyyy/MM/dd` and `yyyy/MM/dd HH:mm`, 24-hour, no seconds. (Q5) Local times that do not exist or occur twice are rejected with a specific error, never moved or guessed. 74. **Desktop session lifecycle (owner decision 2026-10-16; settles the "sign-out and session handling" part of #71):** (1) **Inactivity lock:** default **15 minutes** without keyboard or mouse input, configurable as `Authentication:InactivityLockMinutes` from **1 to 120**; an invalid value (including 0) stops start-up, so the lock cannot be disabled. Inactivity is measured on a **monotonic clock**, so changing the Windows date or time can neither bypass nor trigger it. The application also locks when **Windows locks or the Windows user session switches away** (lock, console or remote disconnect); returning to Windows never unlocks the application. A visible **"Lock now"** command and **Ctrl+L** use the same lock mechanism. (2) **Lock and unlock:** a lock hides all content behind an overlay and keeps the current user's unsaved drafts **in memory only** (nothing is written to disk to support locking). Unlock requires the **same user's password**, verified with the existing mechanisms (one verification per attempt, the same failed-attempt counter and lockout, a lock never extended, generic failure, hash upgrade). A successful unlock **reloads** the user's account status, department and role from the database. A deactivated account, or an account locked out by unlock attempts, **ends the session and returns to sign-in**; a mandatory password change must complete before normal access returns. The cached principal and the UI state are never authoritative. (3) **Current authorization:** every role-sensitive Application command or write **revalidates the user's active status and permission against persisted data at the time of the operation** (`CurrentAuthorization`); the desktop `Principal` is a UI snapshot and never authorizes a business operation by itself. Default-deny authorization and the last-active-Administrator protection are unchanged. No session token, refresh token or persisted session is introduced. (4) **Sign-out, closing and unsaved work:** explicit **sign-out** returns to the sign-in window and discards the previous session's view-model state. Unsaved changes are settled with **Save, Discard or Cancel only where the operation is genuinely supported** (Save is offered only when every form with changes can save); Cancel leaves the user in the session. **"Sign in as another user" from the lock screen** requires an explicit confirmation, with a text that reveals no data, before unsaved drafts are discarded; declining leaves the session locked (when there are no drafts nothing is discarded and no confirmation is asked). **Closing the application ends the in-memory session**; nothing persists across restarts. (5) **Audit** (existing append-only log; never a password, hash or token): explicit sign-out (`SessionSignedOut`); lock with its reason - inactivity, manual, Windows lock or user-session switch (`SessionLocked`); successful unlock (`SessionUnlocked`); failed unlock attempts (`LoginFailed` and `AccountLocked`, the existing mechanisms); switching user from the lock screen (`SessionUserSwitched`); and a **best-effort** `ApplicationSessionEnded` on a clean shutdown. A crash, forced termination or power loss writes nothing, and no event claims otherwise; a failed audit write never prevents a lock, sign-out or shutdown. (6) **Still outside this decision:** customer/request screens, queue and QC actions, session-administration screens, persistent sessions and refresh tokens (not wanted), a SQL Server provider, and **M8** (item/stage expected versions; resolved later in #77). Production-only: central storage of the timeout for multi-PC deployment, server-side session records for forced sign-out and guaranteed end-of-session audit, an absolute maximum session length, per-role timeouts.

77. **M8 resolved - per-row expected versions for request items and stages (owner direction 2026-10-16; settles the "expected versions" part of #71):** (1) `IRequestRepository.FindWithVersionsAsync` returns the request together with `RequestVersions`: the version of the request row, of every item row (by item id) and of every stage row (by item id and stage number). `RequestService.GetAsync` exposes them in `RequestDetail.Versions`. (2) `IRequestRepository.UpdateRowsAsync(requestId, RowVersionExpectations, change)` lets the caller name the versions it loaded for exactly the rows it intends to change (request, specific items, specific stages). A row the caller did not name is not compared with the caller's view. A request-level version alone does NOT detect item or stage changes (priority changes and stage transitions do not change the request row). Callers that want the whole view protected pass `RowVersionExpectations.FromLoaded(versions)`. (5) No schema change, no migration change, no new package, no EF type in Application contracts. (6) Queue actions and QC actions are not built yet; when they are, they must use `UpdateRowsAsync` with the expected versions of exactly the rows they intend to change (the method has its own name because a `null` version would make an overload of `UpdateAsync` ambiguous).

(2) **Finished/sent** (`ItemFinishedSent`) - Warehouse's completion mark, allowed only when the item has been received AND the **latest** cost snapshot of the item has a price approved by Management (#104); a recalculation after the approval therefore needs a new approval before the mark; the record keeps the receipt id, the price decision id and the approved price; one per item; the item is FINISHED_SENT from this record on. (3) **Customer dispatch** (`CustomerDispatches`) - optional tracking: a Jalali date not in the future and a document reference (1-100 characters, case-sensitive), optional note; several per item are allowed; it requires the receipt but not the finished mark and is **not required** for closing the item in v1. **Authorization (default-deny, reloaded from the database):** receipt, mark and dispatch = Warehouse alone; read = Warehouse, Planning, Management. Every step is one transaction with its audit entry (`WarehouseReceiptRecorded`, `ItemFinishedSent`, `CustomerDispatchRecorded`). Additive migration `AddWarehouseCompletion` (three tables, restricting keys, unique receipt and unique mark per item) with an upgrade test; Desktop page "دریافت انبار و تکمیل". **Labelled defaults (not approved):** the finished/sent mark also requires the receipt (the packet only names the price approval; a receipt-less mark would be a finished item that was never received); records cannot be reversed or corrected in v1 (history is never overwritten; a reversal action with a reason is a later decision); the request status is not changed automatically when all its items are finished/sent (closing a request stays a separate step); a dispatch carries no quantity; the warehouse movement history view of 17.4 is the list of these records, not a stock ledger.
106. **Phase 8 implemented: unit metrics and operator hours (docs/JOB_REPORTS_KPI_AND_OVERTIME_DESIGN.md section 7; Decision Log #95 D6/D8).** A read-only report for a Jalali date range (default: the last 30 days), computed by the Application from the persisted facts; **no new tables, no migration, nothing is written**. (1) **Separate, labelled metrics per production unit - no composite score and no ranking of units (D6):** productive hours = approved report line minutes less downtime ("actual"); QC-accepted / rework / scrap base units of the decisions made in the period, attributed to the unit that performed the stage; acceptance, rework and scrap rates as shares of the base units decided in the period; planned versus actual minutes for the stages that were QC-completed in the period (planned minutes per piece x planned quantity against the approved productive minutes reported for the stage); utilization = productive minutes / scheduled shift minutes (working minutes of the shift occurrences of the operators planned in the unit; overtime is included in productive hours, so utilization can exceed 100%). (2) **Overtime shown separately:** the share of productive minutes inside the operator's APPROVED overtime windows, **estimated by time overlap** and labelled as such, because report lines are not linked to assignments (#103). (3) **Only approved reports count; unapproved ones are counted, not used:** each unit shows the number of reports of the period still waiting for approval (SUBMITTED) and is marked not authoritative while that number is above zero; the report carries its run time and period (as-of). (4) **Operator list:** operators ranked by productive hours of the period, then distinct worked days, then operator code - labelled an hour ranking only; no reward or bonus calculation (Phase 2). (5) **Access (D8):** Planning and Management read every unit; a unit supervisor (a designated Production user with the supervisor flag) reads their own units only; every other user, including operators and Production users who supervise no unit, is refused (default-deny, reloaded from the database; permission `ViewKpi`). **Labelled defaults (not approved):** the rates count every QC decision of the period, so a reworked unit that is inspected again is decided again; the period of a decision, of a completion and of a line is its local (Iran) day, and the completion time of a stage is its last QC decision; a unit-less (demonstration) stage has no unit and is not counted; the pending-approval count covers SUBMITTED reports only (drafts and returned reports are not yet reports to approve); planned time of a completed stage is the full planned total even when part of it was reworked; the "estimated finish" metric is not repeated here (the unit queue shows the forecast); no export, drill-down to report lines and per-unit headcount normalization are not built; operators' own-hours view and the 24-day payroll preset are not built (the free date range covers them).
107. **Phase 9a: test-suite speed - a low-cost password hasher for tests that are not about passwords (no production change).** The Windows CI run of the Infrastructure tests had grown to about 50 minutes against the 90-minute job timeout (#99), almost all of it PBKDF2 at the work-factor floor: each workflow test creates ten or more users and each user costs a hash, a verify, a change-password and a second verify. **Production code is unchanged:** the policy floor (310,000), the baseline (600,000) and `Pbkdf2PasswordHasher` stay as approved (#27, #41, #42). A **test-only** `LowCostHasher` (the same PBKDF2 implementation at 1,000 iterations, never upgrading) is used by the workflow, master-data and screen tests (Infrastructure `SecurityFixture.CreateFastAsync`, Desktop `WorkflowHarness`); the authentication, bootstrap, recovery, session, account-administration and current-authorization tests keep the real hasher at the policy floor, and the hasher/policy tests keep covering the baseline. Measured locally (Linux, same machine): Infrastructure suite 12 min 36 s -> 3 min 54 s, Desktop suite 7 min 1 s -> 1 min 18 s, all tests passing. The Windows CI duration of this change is reported in its pull request.
108. **Phase 9b: end-to-end acceptance test and demonstration master data.** (1) **Master data in the demonstration database:** the seed now also creates the fictional units, machines with rates, the day shift for both units, a material with a price, an operator linked to the demonstration production account and that account's designation, so the whole flow can be walked through without any set-up (`docs/DEMO_WALKTHROUGH.md`, `docs/DEMO_SEED_AND_RESET.md` section 4). It is written through the repositories with real users and one audit entry per row - NOT through the application services, because the platform's authorization correctly refuses an account that still has its one-time password (#74, #76) and the seed must not go around it. Repeatable, fixed time, identical after a reset. Owner decisions stay empty (overtime limits, unit supervisors, worker schedule). (2) **End-to-end acceptance test** (`EndToEndDemoTests`): on a freshly initialised demonstration database, the eight accounts replace their one-time passwords and the real application services carry one new contract request from the customer's request through Management approval, Drawing, the contract, item and stage definition, release, start, a daily job report reviewed by Planning as the flagged fallback, QC quantity acceptance, the Warehouse receipt, cost calculation, the contract price recorded by Management, the finished/sent mark (refused before the price), the customer dispatch and the unit metrics; it asserts the figures, the audit trail and that the sample data was not touched. **Labelled defaults / limits:** the walkthrough has been performed by the automated test but not yet by a person in the WPF application on Windows; the sample requests still use the unit-less demonstration stages (retiring that flow is phase 9c).
109. **Phase 9c: the demonstration stage flow is retired (roadmap phase 9, "retire the demo stage flow"; supersedes #79-#81 for the application, history kept).** **Removed:** (1) the whole-quantity QC approval as an application action (`StageAction.ApproveWholeQuantity`, its Application code, audit text "approved by QC (whole quantity ...)" production and next-stage version handling): QC decides by quantity only (`QcInspectionService`, #101); (2) the demonstration stage-work screen ("مراحل و کنترل کیفیت (نسخهٔ نمایشی)": view model, view, navigation item `stages`, page wiring and its tests) - release, start and submit are on the unit queue page, QC is on the inspection page; (3) the API only that screen used (`StageWorkService.LoadAsync`, `GetCapabilitiesAsync`, `AvailableFor`, `StageWorkCapabilities`, `AvailableStageActions`, `StageWorkView`); (4) the issue `UseQuantityInspection` (replaced by the new refusal below). **Changed:** release, start and submit for QC on a stage that is **not planned in a production unit** are now refused with the new `StageUnitRequired` (permission is still checked first; an unknown item is still `NotFound`; nothing is changed or audited). Reason: such stages needed no unit designation, so any Production user could advance them; item definition has required a unit since phase 4a, so unit-less stages exist only in the seeded sample data and in repository-level tests. **Kept on purpose:** the Domain's `ApproveStageWholeQuantity` and the `QcApprovals` history (the sample requests are built with the Domain's demonstration transitions, old audit entries keep their meaning, and many Domain and persistence tests rely on them); `StageAction.Release/Start/SubmitForQc`, the Planning corrections (`CorrectAsync`), permissions `ReleaseStage` / `RunStage` / `InspectOrCorrectQc`, the production overview page "صف تولید". **Sample data:** the six `DEMO-` requests stay as frozen examples for the list and overview screens; their unit-less stages can no longer be advanced; the end-to-end walkthrough uses a new request (`docs/DEMO_WALKTHROUGH.md`). Converting the sample routes to unit stages with quantity decisions is possible later but was not done (it would rebuild every sample state through inspection lines). **Tests:** the old demo-flow suite was replaced by `StageActionTests` (the actions on unit stages: departments, gates, the QC gate, stale request / item / stage / preceding-stage versions, missing versions, vanished items, audit) and a trimmed `StageWorkflowTests` (persistence guarantees: audit rollback, no partial change, competing write; and the refusal of unit-less stages). Migrations: none. **Not approved / open:** nothing new; the earlier decisions #79-#81 remain the record of how the demonstration was accepted.
110. **Phase 9e: one migrated template database per test run (test-only; no production change).** After #107 the Windows CI run of 9c took 60 minutes (Infrastructure tests 57 min) although the same-sized run before took 36 minutes (32 min): the hosted runner varies by almost 2x, so the 90-minute job timeout (#99) was closer than the median suggested. The remaining dominant per-test cost is applying all 21 migrations to a fresh SQLite file for every test. `TempDatabase.MigrateAsync` (Infrastructure tests) and `WorkflowHarness` (Desktop tests) now migrate ONE template file on first use in a test run (single-flight, deleted at process exit) and give each test a file copy of it; the copy is the same database (schema, seeded rows, migration history). If the template is not a single self-contained file (a journal or WAL file remains) the tests fall back to migrating in place; a database that already exists is still migrated in place (idempotent). Tests of the migrations themselves open their own context and never use the shortcut, so every migration is still applied from scratch and checked by its upgrade test. Measured locally (Linux): Infrastructure 3 min 54 s -> 2 min 34 s, Desktop 1 min 10 s -> 50 s, all tests passing; the Windows CI duration is reported in the pull request. Production code, migrations and the security policy are unchanged.
111. **Phase 10a: item-scoped contract decision (owner direction of 2026-10-27; supersedes the request-scoped "ContractRequired" of #4 and Master Specification section 18 line "`ContractRequired` belongs to the request, not individual request items"; history kept).** The owner's requirement list names "the item's individual contract decision" as a production gate. **Conflict recorded:** #4 and CLAUDE.md say "the contract applies to the entire request" and the Master Specification says `ContractRequired` belongs to the request. **Resolution (owner pre-authorized resolving the model; the smallest change that keeps every approved document and workflow):** (1) the contract DOCUMENT, its versions, PDF and Management's approve/reject stay at request level exactly as built (#85); Planning's request-level decision stays and means "this request may need a contract"; (2) NEW append-only `ItemContractDecisions` (Planning, reason mandatory, who/when kept; the latest row of an item is current; a change of mind is a new row and the audit log records every decision, code `ItemContractDecided`): an item decided **not required** is not held by the contract; an item with **no row follows the request** (this is what every pre-existing item does, so the migration creates the table empty and reinterprets nothing); (3) an item can be decided **required** only when the request's own decision is "required"; a decision is refused once any stage of the item was released or started (`ItemContractInProduction`), when it repeats the current state, or before the request decision exists; (4) the gate is now evaluated **per item**: `RequestGateService.EvaluateAsync(requestId, itemId)` and `EvaluateItemsAsync`; stage Release/Start, the unit queue ("blocked: gate") and the cost basis (contract-basis price only for items that need the contract) use the item's gate; the request-level state treats the contract as satisfied when every item was decided "not required"; (5) **labelled consequence (needed so the decision can exist at all):** items are defined or imported after Management, Drawing, **Planning's request-level contract decision**, inquiries and clarifications, but **no longer wait for Management\'s approval of the contract** (`ProductionGateStatus.DefinitionAllowed`); that approval now holds the release and start of the stages of the items that need the contract. REPAIR requests still have no contract. **Not changed:** who may decide (Planning; permission `CreateOrSubmitContract`), who approves (Management), the contract status machine. Open for the owner: whether Management should also see/approve the per-item decisions (default: no - Planning decides, the audit log shows it).
112. **Phase 10b: work-session model (owner direction of 2026-10-27; adds to, does not replace, the daily job reports of #100-#103).** Planning/Production work is recorded as **work sessions under a stage**, not as a second queue: a session names request item + stage + unit + machine + operator, the dispatcher/starter/finisher, and has its own active intervals, pauses (reason mandatory, note for "other"), history and corrections; finishing a session does not complete the stage. New tables only (`WorkSessions`, `WorkSessionIntervals`, `WorkSessionPauses`, `WorkSessionEvents`, `WorkSessionCorrections`, `OutageEvents`, `PauseReasons`); the migration reads and rewrites no job report, stage or cost row, and seeds the owner's seven pause reasons (power outage, planned preventive maintenance, unplanned machine breakdown, operator absence or shift handover, material unavailable, waiting for supervisor/technical assistance, other - note required). The database refuses a second open interval for the same session, machine or operator (filtered unique indexes). Design and labelled defaults: `docs/WORK_SESSIONS_DESIGN.md` (time approval by Planning not equal to the dispatcher; stage tracked by sessions OR job reports; exact handover only, no overlap; no labour cost; corrections by Planning with reason before QC submission). **Implemented in 10b: model, persistence, migration, tests. Not yet: use cases (10c), metrics/costing (10d), UI (10e).**
