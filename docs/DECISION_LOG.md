# ERP/MES Decision Log

This is a durable record of user-approved decisions. Update it only when the user approves a decision. Keep unresolved items in the separate section below.

## Approved decisions

1. **Request identity:** Customer-provided free-form RequestNo; not generated internally. Unique business key is Customer + RequestNo + Jalali Request Year. RequestNo comparison is case-sensitive. RequestID is the internal primary key.
2. **Request/item model:** Request-based system; no mandatory Project entity. Customer requests may contain both MAKE and REPAIR items. WorkTypeID is at item level.
3. **Excluded scope:** No Internal Request workflow in v1; no Emergency subsystem; no Final-QC concept. QC is required after individual production stages.
4. **Contracts:** Contract requirement applies to the entire request. Planning creates/submits the contract and attaches/imports PDF. Management approves/rejects with optional explanation. Rejected contracts return to Planning for correction/resubmission. Approval notifies Planning and Warehouse dashboards. Contract customer is derived from Request.
5. **Production/QC:** Each subsequent stage waits for QC approval of the immediately preceding stage. Planning normally releases the first internal stage. If first stage is external, wait for arrival/return and QC approval before progressing. External supply is a stage with dispatch/arrival tracking and QC.
6. **QC correction:** Preserve the historical QC decision and mark the item as corrected. Return the item to Stage 1; handle downstream stages manually rather than automatically replaying every downstream stage.
7. **Quantities:** QC permanently rejected quantities are scrap. Accepted quantities continue; only rework quantity returns for rework.
8. **Localization:** Every user-visible date is Shamsi/Jalali with 24-hour time. Every monetary value is Rial, never silently Toman. UI is Persian and RTL.
9. **UOM ownership:** QC defines configurable units/conversions. A positive conversion factor implies its reciprocal automatically.
10. **Cost ownership:** Planning maintains machine machining rate/hour. Warehouse maintains raw-material price/kg.
11. **Priority:** Values are `عادی`, `فوری`, `خیلی فوری`. Planning owns normal priority/order and may change it; multiple stages/items may share a priority. Management alone may batch-override queue order. Every affected row records old/new order, reason, manager, timestamp; original Planning priority remains intact. (Where the Planning priority is stored: #58.)
12. **Machining time:** Planning enters minutes per piece. Estimated stage load is minutes per piece × planned quantity.
13. **Calendar:** Saturday–Thursday are normal workdays. Friday is normally off but may be worked with supervisor approval. Holidays/off-days and shift patterns are configurable. Current reference schedule: 08:00–17:00 with 12:00–13:00 break; a possible 2-shift setup is 06:00–14:00 and 14:00–22:00; more shifts may be introduced. Do not hard-code current settings permanently.
14. **Downtime:** PM reports machine downtime to Planning; approved/recorded downtime affects planned end calculations.
15. **External lead time:** External production stages require expected lead time.
16. **Excel:** One mixed worksheet, Persian headers, explicit Work Type column, about 1,000 items. Preview/validate before import. Existing same-ItemNo rows with changed imported values are manual-choice conflicts, not silent overwrites.
17. **Warehouse scope:** Inquiry/receipt/movement history only; no real inventory balance/deduction system in v1.
18. **PDF/document links:** Store a document binary once and permit multiple logical record links.
19. **Authentication/roles:** Application username/password; one department and one role per user. Sensitive action permissions are defined in the Domain and Database Specification §15.2 / §32.8 and the project instructions (`CLAUDE.md`).
20. **Platform/data migration:** Windows 10/11 desktop; WPF/MVVM; local SQLite only for single-user development; final production database SQL Server. Confirm supported Windows 10 baselines and exact .NET target before locking framework.
21. **Performance bonuses:** Ranking/reward formula is Phase 2, not a v1 approval/payroll calculation.
22. **Initial .NET target (approved 2026-10-09; amended 2026-10-10; initial, not a production lock):** .NET 10 (LTS). Per the official Microsoft .NET support policy checked on 2026-10-10 (https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core): .NET 10 is LTS, released 2025-11-11, supported until 2028-11-14 (latest patch listed there: 10.0.12). Target frameworks: `net10.0-windows` for the WPF Desktop project; `net10.0` for platform-neutral class libraries (Domain, Application, Infrastructure and test projects) as applicable. This does not settle the Windows baseline or the SQL Server version: the minimum supported Windows edition/version and the production SQL Server version remain unresolved (see Unresolved) until the deployment environment is checked. Microsoft's .NET 10 supported-OS list (https://github.com/dotnet/core/blob/main/release-notes/10.0/supported-os.md) names only specific Windows 10 builds/servicing channels, not all Windows 10 editions, so no blanket Windows 10 support is claimed.
23. **Keys and concurrency (approved 2026-10-09):** Integer surrogate primary keys (Domain and Database Specification §25.1). Mutable entities carry an application-managed row-version column used for optimistic concurrency, portable between SQLite and SQL Server.
24. **Time storage (approved 2026-10-09):** Timestamps are stored in UTC; calendar-only dates (for example request date) use a date-only type. Conversion to Jalali and local time happens only at the presentation boundary.
25. **Provider conventions (approved 2026-10-09):** Maintain a written provider-neutral subset (no SQLite-only SQL in business logic; avoid decimal aggregates, `DateTimeOffset` and partial indexes in business queries). Keep one EF migration set per provider. The SQLite development database is disposable and is not migrated to production. Run a SQL Server test pass before the stage/QC milestone.
26. **Audit (approved 2026-10-09):** A generic append-only audit table records master-data, configuration and login events, in addition to the domain-specific histories already required (workflow entries, QC, queue overrides, etc.).
27. **Password storage (approved 2026-10-09):** PBKDF2 using the built-in .NET implementation, with a per-user random salt and the iteration count stored with the hash so it can be raised later. Passwords are never stored in plaintext. Parameters are fixed in the Milestone 1 ADR.
28. **Documentation amendments (approved 2026-10-09):** Superseded passages in the specifications are annotated, not rewritten, and mechanical errors (wrong section numbers, stray markers, stale cross-references) are corrected. No business rule text is changed by an amendment. Items that still need an owner decision are left open.
29. **Request statuses for Milestone 2 (D5, approved 2026-10-10):** The initial request-status set is `CREATED`, `SENT_TO_MANAGEMENT`, `MGMT_APPROVED_AT_PLANNING`, `MGMT_REJECTED_AT_PLANNING`, `UNDER_DRAWING_REVIEW`, `DRAWING_RETURNED_TO_PLANNING`, `CANCELLED`, `CLOSED`. Management rejection requires a reason. A Management-rejected request **can be reopened** for a new Management decision by the Planning department or the Management department; reopening requires a reason and is audited. Later statuses (contract, production, completion) are added with their milestones. The full transition table is still to be drafted from Master Specification §3 and audit Appendix A and reviewed at the start of Milestone 2 (see Unresolved).
30. **Departments and roles seed (D6, approved 2026-10-10, development seed):** Departments: Central, Management, Planning, Drawing, Warehouse, Production, QC, Maintenance/PM, and System (home of the Admin account). Roles: Admin, Manager, Staff. Final company names may replace these without a schema change. Authorization rows that name a role use these names (initial request approval/rejection = Management department + Manager role); all other matrix rows remain department-based as in Domain and Database Specification §15.2.
31. **RequestNo key details (D7, approved 2026-10-10):** (a) The Jalali Request Year is derived from the customer's `RequestDate`, fixed at creation, and changeable only through an audited correction that re-checks uniqueness. (b) Leading or trailing whitespace in `RequestNo` is rejected with a validation error, never auto-trimmed. (c) No letter or digit normalisation is applied to `RequestNo`; it is stored and compared as exact text. (d) `RequestNo` uses a case-sensitive binary collation on both SQLite and SQL Server, verified by a test on both providers. (e) A non-blocking warning is shown when a case-insensitive near-duplicate exists for the same customer and Jalali year.
32. **Customer master (D8, approved 2026-10-10):** Minimum fields: `CustomerID`, `Name`, `IsActive`, and created/updated audit fields. No customer code and no contact fields for now (added later when a requirement exists). "Customer" is the canonical term ("Buyer" is legacy). There is no item-level customer; an item's customer is its request's customer.
33. **Quantity precision (D9, approved 2026-10-10):** Requested quantities, UOM conversion factors/results and minutes-per-piece are stored as decimals with a fixed scale; the scale is set in the Milestone 2 design (proposal: 4 decimal places). Per-UOM whole-number rules may be added later. Decision #25 still applies (avoid decimal aggregates in business queries). Rial rounding and storage type remain unresolved.
34. **Provisional development permission map (D10, approved 2026-10-10; revisit before production):** Central creates a request and submits it to Management. Planning receives the request, records the hand-off to Drawing, and edits request details. Drawing records the doability decision (already in the matrix) and defines MAKE items. Planning defines REPAIR items and may create/edit any item. Planning and Drawing may import items from Excel. Items are editable only until production release; after release only Planning may change them, through the controlled route-revision mechanism that is still to be specified. Every action not listed here or in Domain and Database Specification §15.2 remains denied.
35. **Documents (D11, approved 2026-10-10):** Documents are linked through link tables only; no single document foreign key on items, requests or contracts. A stored binary is shared by all its links. Request PDFs accept PDF only, with a maximum size held as a configuration value (the 10 MB figure originally approved here is superseded by #54: 20 MiB). Content-hash de-duplication on upload and retention/deletion rules are not decided here.
36. **Milestone 1 scope (P1, approved 2026-10-11):** Milestone 1 is limited to the technical foundation. It does not implement Customer, Request, RequestItem, request workflow, Excel import, MAKE/REPAIR functionality, documents, or any production functionality. Architecture Specification §38 reflects this scope.
37. **Project structure (P2, approved 2026-10-11, subject to documented responsibilities):** Projects `Domain`, `Application`, `Infrastructure` (shared, provider-neutral), `Infrastructure.Sqlite`, `Desktop` and `Provisioning`, with the dependency direction and per-project responsibilities documented in `docs/MILESTONE_1_PLAN.md` §2. `Domain` remains independent of infrastructure and UI. Provider-specific persistence (configuration and migrations) belongs in provider-specific projects. A future `Infrastructure.SqlServer` project would add its own configuration and separate migrations beside `Infrastructure.Sqlite` without duplicating business logic (which lives only in Domain and Application); it is not created now, and the production SQL Server version/provider stays unresolved.
38. **Provisioning project (P3, approved 2026-10-11):** A separate `Provisioning` project, excluded from the normal factory-PC distribution. It supports authorized initial setup and administrator recovery. It must not embed privileged credentials; the operator supplies the database connection at run time.
39. **Administrator bootstrap (P4, approved 2026-10-11 with safeguards):** The first Administrator is created only with a cryptographically random, single-use bootstrap token. Only a digest of the token is stored, never the plaintext. The token expires after 24 hours and allows five attempts; the attempt limit is enforced centrally in the database across all application instances. Re-issuing a token invalidates the previous one. The claim is atomic so two clients cannot both create the initial Administrator. The token is never logged and never committed to source control. No default password or credential exists in the repository.
40. **Authentication policy (P5, approved provisionally 2026-10-11):** Minimum password length 12, five failed attempts, five-minute lockout. All values are configurable. Security events are audited.
41. **Password hashing (P6, approved 2026-10-11):** PBKDF2-HMAC-SHA256, initially 600,000 iterations, a fresh random salt per password. Stored per password: algorithm and version, salt, iteration count and derived hash. Older parameters are upgraded after successful password verification. The baseline is not changed silently. (Supersedes the parameters left to the Milestone 1 ADR in #27.)
42. **Hash benchmark (P7, approved 2026-10-11):** The chosen baseline is benchmarked on the lowest-spec supported PC, targeting approximately 500 ms. The work factor is never reduced automatically to meet the timing target.
43. **Package approval (P8, conditionally approved 2026-10-11):** Packages are added only after the owner reviews the actual package table (name, version, purpose, licence, compatibility). No unjustified dependency is added. The table is in `docs/MILESTONE_1_PLAN.md` §8; **it is not yet approved**, so Milestone 1 step M1.1 adds no package.
44. **Central package versions (P9, approved 2026-10-11):** Central package version management (`Directory.Packages.props`), with compatible versions for related EF Core components.
45. **Jalali dates (P10, approved 2026-10-11):** `System.Globalization.PersianCalendar` behind `JalaliDateService`, with tests for Nowruz/year boundaries, leap years and Persian-digit input.
46. **SDK pin (P11, approved 2026-10-11):** .NET SDK 10.0.401 pinned in `global.json`; CI uses the same SDK. Future SDK updates require a reviewed change. (Refines #22.)
47. **Administrator recovery (P12, approved 2026-10-11):** Normal account management must not deactivate or demote the last active Administrator. If all Administrator access is lost, recovery requires an authorized operator using the restricted Provisioning mechanism with authorized database access. Recovery is audited, uses a one-time credential/token, and forces the recovered account to set a new password. There is no universal recovery password, hidden master key or backdoor. The process for an eventual SQL Server deployment is documented in `docs/MILESTONE_1_PLAN.md` §5.7 without deciding the SQL Server version/provider.
48. **UI font (P13, approved provisionally 2026-10-11):** Tahoma as the primary font with an appropriate system fallback. No font is bundled until licensing and deployment needs are established.
49. **Continuous integration (P14, approved 2026-10-11):** Windows CI performs restore, build and test. GitHub Actions are pinned to full commit SHAs. Workflow permissions are least-privilege. No deployment workflow and no secrets for Milestone 1.
50. **UI verification (P15, approved 2026-10-11):** A manual UI checklist verifies the initial shell; automated build and test requirements are retained.
51. **Exact SDK pin confirmed (M1.1 approval, 2026-10-11):** .NET SDK 10.0.401 with `rollForward: disable` in `global.json`. The exact SDK must be installed on every developer machine and in CI. Future SDK changes require a reviewed update to `global.json`. (Confirms #46.)
52. **Test framework (M1.1 approval, 2026-10-11):** xUnit v3 for this .NET 10 project, set up as in the official `xunit.v3` project template, using the VSTest runner combination (`Microsoft.NET.Test.Sdk`, `xunit.runner.visualstudio`, `xunit.v3.mtp-off`; exact versions in `Directory.Packages.props`). The three test projects are kept. Each test project has real, discoverable tests; a run that discovers zero tests is never reported as a passing behavioural test run, and CI fails on it.
53. **Package acceptance gate (M1.1 approval, 2026-10-11):** P8 (#43) stays conditional. For every batch of packages added, restore and vulnerability checks, including transitive dependencies, are run and recorded in `docs/MILESTONE_1_PLAN.md` §8.1 and relevant advisories are addressed before acceptance. The production SQL Server provider stays undecided.
54. **Maximum PDF size (approved 2026-10-14, supersedes the 10 MB figure in #35):** The maximum size of a request PDF is **20 MiB (20 x 1024 x 1024 = 20,971,520 bytes)**, displayed to users as "20 MB". The limit stays a configuration value, and only PDF files are accepted. A file of exactly 20,971,520 bytes is within the limit and a file of 20,971,521 bytes is rejected; when PDF upload is implemented it must be tested at both sizes. Document upload is not implemented by this decision. Other parts of #35 are unchanged.
55. **EF Core and SQLite for the local demonstration database (approved 2026-10-14):** `Microsoft.EntityFrameworkCore.Relational` and `Microsoft.EntityFrameworkCore.Sqlite` are approved at the aligned stable version 10.0.13 under the package gate of #53 (batch 2; results in `docs/MILESTONE_1_PLAN.md` section 8.2, licence inventory in `docs/DEPENDENCY_LICENCE_INVENTORY.md` section 6). A blocking problem with 10.0.13 is reported, not silently downgraded. The production SQL Server provider and the production database version are not decided by this entry. The `Design` package and `dotnet-ef` tool are not covered.
56. **EF Core migrations tooling (approved 2026-10-14):** Migrations are created with EF Core migrations, including for the local demonstration database; `EnsureCreated` is not used. `Microsoft.EntityFrameworkCore.Design` 10.0.13 is approved with `PrivateAssets="all"` (design-time only) and `dotnet-ef` 10.0.13 is pinned in a committed local tool manifest (`.config/dotnet-tools.json`); both keep the version of EF Core and the SQLite provider. The generated initial migration and model snapshot are committed to the repository and reviewed in their own PR. This approves tooling for the SQLite demonstration migrations only; the production SQL Server provider and version stay undecided (results in `docs/MILESTONE_1_PLAN.md` section 8.3, inventory in `docs/DEPENDENCY_LICENCE_INVENTORY.md` section 7).
57. **Four-day demonstration track (owner decisions, 2026-10-14):** A working, presentable demonstration is built under `docs/FOUR_DAY_DEMO_PLAN.md`; it does not replace any production requirement, and every demo-only behaviour is labelled. (T1) Only the approved request statuses of #29 are used, with simplified, labelled transitions; the request state machine is not claimed to be implemented. (T2) Fictional seeded routes of two or three stages per item; no route editor. (T3) QC approval only; no rejection action unless it follows the accepted/rework/scrap rules. (T4) A labelled estimate (minutes per piece x quantity) instead of a calculated completion date. (T5) Only already-approved permissions are enforced; everything else is denied. (T6) Fictional accounts with real PBKDF2 hashing and random one-time passwords generated locally, kept in a protected file outside the repository and excluded from version control, never printed to CI logs, never a universal password; the production authentication and recovery design (#40, #41, #47) is unchanged. The local demo database uses EF Core migrations, not `EnsureCreated`. The production SQL Server provider and version stay undecided.
58. **Domain model guards and priority granularity (owner review of PR #14, 2026-10-14):** (G6) The Planning priority belongs to the `RequestItem`; every stage and queue entry of the item inherits it, and no independent stage-priority field is added. Management queue-order overrides stay separate and never overwrite the underlying Planning priority. (G7) New items default to `NORMAL` (`عادی`); Planning may change it to `URGENT` or `VERY_URGENT`. Also approved: (G1) `RequestNo` is rejected when empty, white-space-only or with leading/trailing white space, and is never trimmed or normalised. (G2) `Customer.Name` must be non-empty and not white space, with no other formatting, case or uniqueness rule and no silent normalisation. (G3) Requested and planned quantities must be greater than zero; exact decimal values are kept, nothing is silently rounded, and the scale stays open for Milestone 2. (G4) A supplied planned duration for an internal stage must be greater than zero; zero never means "no estimate"; external lead time stays separate from internal minutes. (G5) `ItemNo` is compared as exact, case-sensitive ordinal text and is never parsed numerically. (G8) For the labelled demonstration only: release `PLANNED` to `WAITING`, start `WAITING` to `IN_PROGRESS`, submit for QC `IN_PROGRESS` to `WAITING_QC`; this does not approve the production stage state machine or the request-status transition table. (G9) Initial route definition is a separate operation from the future controlled route revision: the domain model offers `DefineInitialStage` only before the first stage is released and presents it as initial construction, not as route revision. The approved controlled revision after work has started (auditable: actor, reason, timestamp, before/after sequence) is not implemented and is not prohibited; its downstream-stage handling is still unresolved, and the demo has fixed seeded routes and no route editor. (G10) Whole-quantity QC approval is demo-only; the partial accepted/rework/scrap dispositions of Domain and Database Specification section 9.3 are a production requirement that the current model does not represent. (G11) Cancelled and closed requests accept no new items; ordinary item definition belongs before production release and later changes follow the controlled Planning process, which is not enforceable yet because the release state is not implemented.

## Unresolved — do not guess

- Request progress percentage semantics: proposed item-completion percentage plus separate quantity/status summaries, but not yet explicitly approved. Also unresolved: how partial quantity / scrap / rework impact the displayed percentage.
- Exact minimum Windows 10 release/edition to support; assess current support/security status and test actual factory devices. Prefer Windows 11 where hardware supports it.
- Production SQL Server version/provider after OS baseline and deployment environment are inventoried. (The initial .NET target is recorded in #22; its fit with the factory's Windows machines still has to be confirmed against the supported-OS list.)
- Full role × department × operation authorization matrix details beyond the explicitly approved combinations; default deny for sensitive actions until permission is specified. (A provisional map for Milestone 1–3 actions is in #34.)
- Scheduling algorithm details: queue capacity across multiple units/machines, whether per-piece times vary by quantity/routing, setup/batch times, whether parallel machines are interchangeable, how downtime is approved, and how external lead time is represented in calendar dates.
- Queue ordering: (a) the ordering rules where several items/stages share the same priority (planning order is stored as a separate position); (b) the precedence of an active Management override after a later Planning priority change (the override and the underlying Planning priority are both preserved; which wins is not decided). The storage location of the Planning priority is decided in #58.
- Controlled stage-revision semantics after an item has started: insertion before/after existing stages is allowed with an auditable history (actor, reason, timestamp, before/after sequence), but the exact statuses and the handling of downstream, active or completed stages require explicit rules. No route-revision operation exists in the domain model yet.
- Excel conflict-resolution choices (skip/update/cancel/manual field merge) and whether updating fields is permitted for already released/in-progress/completed items. Never overwrite a production item silently.
- PDF storage retention policy and rules for deleting old documents. (Request PDF format is decided in #35 and its size limit in #54; limits for other document types are not.)
- Exact database migration/testing and backup/restore operating procedure.
- Request-status transition table (which transitions are allowed from each status, and whether `CANCELLED` and `CLOSED` are terminal), to be drafted from Master Specification §3 and audit Appendix A and reviewed at the start of Milestone 2.
- Persistence mapping details of the initial subset (docs/PERSISTENCE_MAPPING.md section 4): reference tables for controlled codes versus enum integers, decimal storage and scale, shadow keys for stage and QC approval, aggregate-level (request-wide) concurrency versus the per-row version of #23, extra indexes, and verification on SQL Server.
- Production stage state machine (the three transitions of #58 are demonstration-only) and enforcement of "items editable only until production release" once a request-level release state exists. Partial QC dispositions (accepted/rework/scrap) are a production requirement that the domain model does not implement yet. Details in `docs/DOMAIN_MODEL_DEMO_SCOPE.md`.
- Permission to reopen is decided only at department level (#29); whether a role requirement applies is not stated.
- Rial rounding rules and storage type (see #33).
- Central (database) storage of the authentication policy for multi-PC deployment; in Milestone 1 the policy comes from configuration (#40).
- Demonstration database marker and status placement (proposed in the seed-and-reset PR, `docs/DEMO_SEED_AND_RESET.md` sections 2 and 3, awaiting owner confirmation): the SQLite header field `application_id` as the demonstration marker (instead of a marker table with its own migration), and the demonstration-only Domain method `Request.PlaceInStatusForDemonstration` that places sample requests in approved statuses without a transition table.
- `JalaliDateService` presentation details (see `docs/JALALI_DATE_SERVICE.md` section 7): on-screen digit shape (Persian or Latin); which time zone counts as local; whether input should accept more than Latin/Persian digits and `/` (Arabic-Indic digits, other separators, surrounding white space, seconds); whether the golden dates in that document are an accepted source. The service takes digit shape and time zone as required arguments and assumes neither.
