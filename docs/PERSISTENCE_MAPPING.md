## 1. Where things live

| Piece | Project | Why |
|---|---|---|
| `ErpMesDbContext`, entity configurations, UTC converter | `ERP.MES.Infrastructure` (`Persistence/`) | Provider-neutral model (EF Core Relational only). Business rules stay in the Domain; the configurations only say how the Domain types are stored. |
| `SqliteDatabase` (connection options, `MigrateAsync`), the migrations and the model snapshot | `ERP.MES.Infrastructure.Sqlite` (`Migrations/`) | One migration set per provider (approved convention). |
| `ErpMesDbContextFactory` (design-time) | `ERP.MES.Provisioning` | The `dotnet-ef` startup project; the tool did not discover the factory in the migrations library. |

The Domain types are mapped as they are: constructors, private setters and backing fields are used by EF Core; no Domain type was changed and no Domain rule is repeated as a database check constraint.

## 2. What is stored

| Table | Notes |
|---|---|
| `Customers` | Name, active flag, audit fields, `Version`. |
| `Requests` | `RequestNo` stored exactly with the `BINARY` collation (case-sensitive); unique index on (`CustomerId`, `RequestNo`, `JalaliRequestYear`) (spec 4.2, 26). `Status` is stored as the enum's integer value. `Version`. |
| `RequestItems` | `ItemNo` with `BINARY` collation; unique index on (`RequestId`, `ItemNo`) (spec 5.2). Planning `Priority` lives here and is inherited by stages (Decision Log #58). Quantities are exact decimals stored as text; no precision is set because the scale is open for Milestone 2. `Version`. |
| `ItemStages` | Surrogate primary key; **alternate key** (unique constraint) on (`RequestItemId`, `StageNo`). `PlannedTotalMinutes` is derived and not stored. No priority column. `Version`. |
| `QcApprovals` | The demo-only approval record (one approved quantity). Append-only: **no `Version`**. It does not represent accepted/rework/scrap dispositions (a production requirement). |

Foreign keys: `Requests` to `Customers`, `RequestItems` to `Requests`, `ItemStages` to `RequestItems`, and for `QcApprovals` two: to `RequestItems` (`RequestItemId`) and the **composite key (`RequestItemId`, `StageNo`) to `ItemStages`**, so an approval can only refer to a stage that exists and belongs to the same item. That composite key is not unique, so several approval rows per stage (append-only history) remain possible. **All foreign keys restrict deletion**: transactional rows are not physically deleted (spec 25.3). Foreign keys are enforced on every connection. Timestamps are UTC text; values read back are marked as UTC by a converter (SQLite returns an unspecified kind and the Domain requires UTC). Dates are `DateOnly` text.

### 2.1 Optimistic concurrency (Decision Log #23)

- `Customers`, `Requests`, `RequestItems` and `ItemStages` have a `Version` column (`long`, not null). It is a **shadow property**: the Domain types do not carry it and do not reference EF Core.
- It is **application-managed** and portable: `ErpMesDbContext` sets a new row to version 1 and adds one to the version of every modified row inside `SaveChanges`/`SaveChangesAsync`. It is declared as a concurrency token, so an `UPDATE` carries `WHERE Id = @id AND Version = @loadedVersion`. If another context saved first, no row matches and EF Core throws `DbUpdateConcurrencyException`; the stale change is not applied and nothing is overwritten. No SQL Server `rowversion` or provider-specific type is used.
- Saving without changes does not change the version; an update to one row does not change other rows' versions.
- **Scope of the protection:** it is per row. Two users who change *different* rows of the same request (for example two different stages) do not conflict. Aggregate-level concurrency (a version on the request that every child change would raise) is not part of this change (M8).
- `ErpMesDbContext.GetRowVersion(entity)` exposes the loaded version to callers (for example a future screen that reports a conflict).

## 3. The migration

`InitialCreate` was generated by the pinned `dotnet-ef` 10.0.13 on the Windows CI runner (SDK 10.0.401), because the SDK is not available in the authoring environment. It was **regenerated** after the first review added the row version and the QC-approval-to-stage key (the migration was not merged yet, so the initial migration was replaced, not followed by a second one): the previous files were removed, the tool generated the new ones from the current model, and the generated output was not edited by hand. A temporary workflow printed the generated files as base64 with their SHA-256; they were decoded here, the hashes checked, and the actual generated files committed unchanged (including their line endings and byte-order marks). The temporary workflow is not part of the pull request. Command:

```text
dotnet ef migrations add InitialCreate --project src/ERP.MES.Infrastructure.Sqlite --startup-project src/ERP.MES.Provisioning --context ErpMesDbContext --output-dir Migrations
```

The first generation attempt (original version) built successfully but reported "No DbContext named 'ErpMesDbContext' was found", because the design-time factory sat in the migrations library; moving it to the startup project fixed this.

The schema is created only by applying this migration (`SqliteDatabase.MigrateAsync`). Opening a database that is already up to date applies nothing. `EnsureCreated` is not used anywhere (a test scans the source).

## 4. Limitations and open mapping questions

| # | Question | What the code does meanwhile |
|---|---|---|
| M1 | Request status, work type and priority are enum integers; the specification mentions controlled status records/codes (reference tables). | Integers; no reference tables. |
| M2 | Decimal columns are SQLite text; numeric comparison in SQL (sorting, sums) is not reliable on text. | Exact values round-trip; business queries must not rely on SQL decimal ordering (Decision Log #25). |
| M3 | `ItemStages` and `QcApprovals` have surrogate keys the Domain does not expose. | Shadow keys; the Domain has no stage or approval identity yet. |
| M4 | (Resolved) The approved application-managed `Version` column is mapped as a shadow property. | See section 2.1. |
| M5 | Indexes beyond the unique business keys and foreign keys (for example by request date or status). | None; to be decided from real queries. |
| M6 | No audit table and no workflow history are mapped. | Out of this subset. |
| M7 | Behaviour on SQL Server (collation, decimal precision, `DateOnly`) is not verified. | The model is provider-neutral, but only SQLite is tested. |
| M8 | Concurrency is per row, not per aggregate: changes to different rows of one request do not conflict with each other. | Row-level versions only; an aggregate version is a separate decision. |
| M9 | The concurrency and the stage-reference behaviour are verified on SQLite only; the same model should work on the future provider, but that is not tested. | SQLite-only, as labelled. |
